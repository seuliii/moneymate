# 7단계: 리포트 상태 안내와 모바일 화면 점검

## 수정 내용

- HTTP 연결용 Python 스텁을 실제 AI 분석과 구분한다. 상단 안내·생성 버튼·저장 결과 배지에 테스트 분석임을 표시한다.
- 현재 실행 설정과 저장된 결과의 종류를 따로 판단한다. 기존 결과는 저장된 모델 키를 기준으로 표시하여 설정 변경 후에도 결과의 출처를 유지한다.
- 규칙 기반 스텁 판별은 로컬 통합 실행 도구의 `partner-stub-local-v1` 키를 기준으로 한다. 파트너가 실제 모델로 전환할 때는 별도 모델 키를 사용한다.
- 잘못된 월 요청은 HTTP 400을 유지하면서 조회 폼과 복구 링크가 있는 화면으로 안내한다. 조회 전에 입력을 검증하며 유효한 월을 다시 조회하기 전에는 생성 버튼을 표시하지 않는다.
- DB 조회 실패 시 HTTP 503과 다시 조회하기 링크를 제공한다. 조회 실패를 “저장된 리포트 없음”으로 표시하지 않으며 생성 버튼도 숨긴다.
- 거래가 없는 달에는 첫 거래 등록 경로를 제공한다. 분석 실패 시 기존 저장 결과와 갱신 필요 표시를 유지한다.
- 제출 중 버튼 비활성화와 함께 진행 상태를 안내하고 `aria-busy`·상태 영역을 제공한다.
- 640px 이하에서 계정 메뉴를 별도 줄에 배치하고 리포트 금액 카드를 한 열로 표시한다. 넓은 화면에서는 리포트의 금액 카드 3개를 균등 배치한다.

DB 스키마·파트너 요청/응답·공개 리포트 JSON 필드는 변경하지 않는다. 저장 결과의 스텁 표시 속성은 화면용이며 JSON에 포함하지 않는다.

## 검증 (2026-10-10)

- C# 수정본 빌드: 경고·오류 0.
- AnalysisChecks, StatisticsChecks 통과.
- 로그인한 테스트 계정에서 정상 리포트 표시 및 기존 결과 재사용(HTTP 200) 확인.
- 잘못된 월(2026-13): HTTP 400, 복구 링크 및 조회 폼 표시, 생성 버튼 없음.
- 기록 없는 달: 첫 거래 등록 링크 및 생성 API `no_records`(400) 확인.
- 실제 Python 테스트 프로세스를 중단하고 테스트 계정 거래를 변경한 뒤 Razor 폼 제출: HTTP 502, 실패 안내, 동일 저장 리포트 ID와 이전 금액 유지, 재분석 필요 표시 확인.
- 별도 웹 프로세스에 접속 불가능한 DB 설정을 주입: HTTP 503, 다시 조회 링크, 잘못된 빈 상태 및 생성 버튼 없음. 실제 PostgreSQL은 중단하지 않음.
- Python 복구 후 기존 5077·5090 주소에 수정본을 실행하고 최신 리포트 생성(HTTP 201), 갱신 필요 해제 및 새 금액 표시 확인.
- 320px·390px 브라우저에서 계정 메뉴·테스트 표시·조회 및 생성 버튼 확인, 문서 가로 넘침 없음.
- 기존 저장 결과의 스텁 배지 표시와 공개 API의 추가 필드 비노출 확인.

실제 LLM 모델과 운영 배포는 검증하지 않았다. 이번 검증에서 시간 초과는 AnalysisChecks의 제어된 HTTP 응답으로 확인했으며 실제 Python 응답 지연을 새로 재현한 것은 아니다. 테스트 변경은 별도 로컬 테스트 계정에만 적용했다.

다음 단계는 배포 대상 결정과 운영 설정·비밀·게시 산출물·백업/복원 점검이다. 실제 AI 공동 검증은 파트너 구현 후 진행한다.
