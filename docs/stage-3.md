# 3단계 — 사용자별 거래 CRUD

## 개발 전 검토와 구현 방향

1·2단계의 인증·DB 모델·비밀 설정 제외 정책을 검토했습니다. 초기 마이그레이션에 거래와 사용자 데이터 버전 필드가 준비되어 있어 스키마 변경 없이 서비스를 연결했습니다. 개발 전 빌드는 경고·오류 없이 통과했습니다. 기존 웹 프로세스는 종료된 상태였으며 작업 후 다시 실행했습니다.

구현은 공통 거래 서비스 → 인증 API → Razor 화면 → 격리된 통합 검증 순서로 진행했습니다. API와 화면이 같은 서비스의 입력 검증·소유자 검증·버전 처리를 사용하도록 구성했습니다. 통계·예산·AI는 이번 단계에 포함하지 않습니다.

## 구현 결과

- 내 거래 등록·조회·수정·삭제, 월·유형·카테고리 필터와 페이지 이동.
- 양의 원화 정수 1~10억 원, 유형별 카테고리, 한국 기준 미래 날짜 제한, 제목·메모 길이 검증.
- 사용자 ID는 인증에서 결정하며 거래 ID와 소유자 ID를 함께 조회합니다. 다른 사용자 거래는 404입니다.
- 모든 변경은 CSRF 검증과 인증을 요구합니다. 화면 출력은 HTML 인코딩됩니다.
- 거래 version이 달라지면 409로 거절하고 최신 내용을 다시 불러올 수 있습니다. 충돌한 입력으로 기존 데이터를 덮어쓰지 않습니다.
- 사용자 데이터 버전 행을 FOR UPDATE로 잠근 짧은 DB 트랜잭션에서 거래 변경·거래 버전·데이터 버전을 함께 반영합니다. 여러 요청/앱 인스턴스가 같은 사용자를 변경할 때 증가가 누락되지 않습니다.
- 삭제는 확인 화면에서 체크 후 제출합니다. GET 요청으로 삭제되지 않습니다.
- 좁은 모바일 화면의 메뉴 배치와 거래 유형·카테고리 입력 라벨 연결을 확인·보완했습니다.

## 검증 결과

`scripts/Test-DatabaseFoundation.ps1`을 별도 PostgreSQL 클러스터(55432)와 테스트 웹(5078)에서 실행해 통과했습니다. 실제 개발 DB의 거래에는 테스트 데이터를 넣지 않았습니다.

- 기존 회원 API/폼, 이메일 중복, 비밀번호 정책, 세션 분리, CSRF, HTML 인코딩, 안전한 로그인 이동, 잠금·요청 제한.
- 거래 API/폼 CRUD, 다른 사용자 접근 차단, 잘못된 금액·공백 제목·미래 날짜·유형 불일치 거절.
- 월·유형·카테고리 필터, 페이지 이동, 거래 내용 HTML 인코딩.
- 오래된 버전의 수정·삭제 거절. 동시 수정 두 건 중 한 건만 성공하고 다른 건은 409.
- 동시 등록 두 건 모두 성공하며 사용자 데이터 버전이 각각 증가.
- 성공한 변경 17건에 대해 해당 사용자의 데이터 버전 17, 다른 사용자 0 확인. 거절 요청은 증가시키지 않음.
- 삭제 확인 체크 없이 제출하면 데이터 유지. 확인 후 정상 삭제.
- 기존 마이그레이션·카테고리 시드·DB 제약과 DB 중단 시 웹 생존 진단.

빌드는 경고 0·오류 0입니다. 로컬 게시 결과에서도 `appsettings.Local.json` 제외를 확인했습니다. 실제 브라우저에서 기존 확인용 계정 로그인, 거래 목록과 등록 화면을 확인했습니다.

## 실행과 다음 단계

현재 개발 주소: http://localhost:5077/Transactions

기존 확인용 로그인 계정을 그대로 사용할 수 있습니다. 비밀번호는 소스나 문서에 저장하지 않습니다. 3단계 때문에 DB 초기화 스크립트를 다시 실행하거나 새 마이그레이션을 적용할 필요는 없습니다.

웹 실행 방법과 API 규격은 README.md를 참고합니다. 4단계에서는 월별 수입·지출·순수입과 카테고리별 통계를 실제 거래 데이터에 연결합니다. 순수입은 보유 잔액과 구분합니다.
